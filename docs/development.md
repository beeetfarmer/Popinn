## Layout

```
backend/
├── app/
│   ├── api/v1/        route handlers, one module per resource
│   ├── core/          config, database, security, rate limiting, uploads
│   ├── models/        SQLAlchemy models
│   ├── schemas/       Pydantic request and response models
│   ├── services/      scanner, ffmpeg, Last.fm, Spotify, stream tokens
│   └── tasks/         background job entry points
├── alembic/versions/  migrations
└── requirements.txt

frontend/
├── src/
│   ├── components/    shared components, `ui/` holds the Radix primitives
│   ├── pages/         one per route
│   ├── contexts/      auth context
│   ├── hooks/         custom hooks
│   └── lib/           API client, utilities
└── package.json

```

## Running with Docker

```bash
make docker-dev-up      # build and start with hot reload
make docker-dev-logs
make docker-dev-down
```

The dev compose file mounts source into the containers, so backend changes
reload via uvicorn and frontend changes via Vite HMR.

Podman equivalents exist for each target: `make podman-dev-up` and so on.

## Running without Docker

You will need Python 3.12, Node 22, PostgreSQL 16, and ffmpeg on `PATH`.

**Backend**

```bash
cd backend
python3.12 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/alembic upgrade head
./.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8471 --reload
```

**Frontend**

```bash
cd frontend
npm ci
npm run dev -- --host 0.0.0.0 --port 5173
```

The dev server proxies API calls to the backend. Make sure `5173` is in
`ALLOWED_ORIGINS` and set `COOKIE_SECURE=false`, or the browser will discard
your session cookie over plain HTTP.

**Node 22 is a hard floor.** `jsdom` 30 depends on a `webidl` API that Node 20
does not have, and the failure — `webidl.util.markAsUncloneable is not a
function` — does not obviously point at your Node version.

## Tests

```bash
cd frontend
npm test              # vitest, single run
npm run test:watch
npm run lint
npx tsc --noEmit      # typecheck
```

The typecheck is a separate step on purpose. `vite build` compiles with SWC,
which strips TypeScript types without checking them, so a build passing proves
nothing about type correctness.

Current coverage is the API client (base-path handling, CSRF, the 401 → refresh
→ replay path, single-flight refresh dedup, timeouts), route protection,
`NavLink`, the mobile breakpoint hook, and the `cn` class-merging helper.

When adding tests, check they actually fail when the code is wrong — a
`renderHook` that never re-renders, or an assertion on a mock rather than on
behaviour, will pass against a broken implementation.

## Database migrations

```bash
cd backend
./.venv/bin/alembic revision --autogenerate -m "add a column"
./.venv/bin/alembic upgrade head
./.venv/bin/alembic downgrade -1
```

Always read an autogenerated migration before committing it. Alembic misses
server defaults, enum changes and index renames, and will happily generate a
destructive `drop_table` for a model you merely moved.

Migrations run automatically on container start, so a merged migration applies
on the next deploy with no manual step.

## Security audits

The same scans CI runs, locally:

```bash
make security-audit             # backend and frontend dependencies
make security-audit-backend     # pip-audit
make security-audit-frontend    # npm audit, production deps only
make security-audit-images      # Trivy against the built images
make security-audit-local       # Checkov and Trivy config scanning
```

Note the scope difference: `npm audit --omit=dev` covers only production
dependencies, whereas Dependabot reports development dependencies too. A clean
`make security-audit-frontend` does not mean a clean Dependabot page.

A related trap: a package listed under `dependencies` drags its whole transitive
tree into the production audit. `tailwindcss-animate` is only imported by
`tailwind.config.ts`, and moving it to `devDependencies` removed a long list of
production CVE reports without changing a line of application code.

## CI

CI runs on Forgejo Actions. GitHub is a push mirror of the Forgejo repository
and runs nothing. Jobs run on a self-hosted runner with the `docker` label,
each in its own container.

**`dev.yml`** runs on every push to `dev` and every pull request into `dev`:
Gitleaks, Semgrep, Checkov, `pip-audit`, `npm audit`, frontend typecheck and
tests, then both images are built and scanned with Trivy and thrown away.
Pushes that only touch documentation (`*.md`, `docs/`, `LICENSE`) are skipped.

**`release.yml`** runs on pushes to `main` and on `v*` tags. It repeats every
check job from `dev.yml` unchanged, then builds, scans, prints an SBOM, and
publishes both images to Docker Hub. Nothing is pushed unless every check passes.

**`github-release.yml`** copies a release published on Forgejo to the GitHub
mirror, with the same tag, title and notes.

Check that the check jobs in `dev.yml` and `release.yml` still match before
pushing changes to either file:

```bash
python3 - <<'PY'
import yaml
dev = yaml.safe_load(open(".forgejo/workflows/dev.yml"))["jobs"]
rel = yaml.safe_load(open(".forgejo/workflows/release.yml"))["jobs"]
drift = [j for j in dev if j != "image" and dev[j] != rel.get(j)]
assert not drift, f"release.yml checks differ from dev.yml: {drift}"
assert set(rel["publish"]["needs"]) == set(dev) - {"image"}, "publish must wait for every check"
print("release checks match dev checks")
PY
```

**Required Actions secrets** (Forgejo repository → Settings → Actions)

| Secret | Purpose |
| --- | --- |
| `DOCKERHUB_USERNAME` | Docker Hub account |
| `DOCKERHUB_TOKEN` | Docker Hub access token, Read & Write |
| `GH_RELEASE_TOKEN` | GitHub fine-grained token for this repository, Contents: Read and write |

Each is checked by an explicit step that fails with a clear message rather than
a confusing downstream error.

## Releasing

Work lands on `dev`, where every push runs the checks. Nothing reaches `main` or
Docker Hub until you promote it.

**1. Promote dev to main** once the dev checks are green:

```bash
git switch main && git merge --ff-only dev && git push origin main
git switch dev
```

`release.yml` re-runs the checks against `main` and publishes `edge` and `<sha>`.

**2. Tag the release.** The git tag is the source of truth; nothing reads a
version from a file.

```bash
git tag -a v0.1.0 main -m "Popinn 0.1.0"
git push origin v0.1.0
```

That publishes:

| Tag | Points at |
| --- | --- |
| `0.1.0` | This exact release |
| `0.1` | The newest `0.1.x`, so a pinned deployment picks up patches |
| `latest` | The newest release |
| `edge` | Moved only by pushes to `main`, i.e. every commit — not a release |
| `<sha>` | Every build, addressable by commit |

Pre-release tags such as `v0.1.0-rc1` publish under their own name but never
take `latest` or the `MAJOR.MINOR` alias, so `docker pull popinn-web` cannot
start serving a release candidate. A malformed tag fails the job rather than
publishing nothing quietly.

Normal pushes to `main` publish only `edge` and `<sha>`, so version tags stay
pinned to what they were released as.

**3. Publish the release.** Once the tag's release run is green, create a
release from that tag on Forgejo. `github-release.yml` creates the same release
on GitHub.

The rolling channel is `edge` rather than `latest` on purpose. A push to `main`
can carry several unreleased commits, so it is not a release. Calling that
`latest` would break the one assumption everyone makes about that tag, and break it silently: you would pull a half-finished refactor
with no way to tell. Self-hosters can therefore use `latest` and get releases.
